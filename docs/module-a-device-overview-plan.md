## 項目 2：mock 母體擴充至 1,284 場域

**目標檔案**：`src/mocks/module-a.ts`

**目前問題**：`FIELDS_A_FULL` 只有 12 筆（3 筆真實設備 + 9 筆手寫示範），但檯面數字寫 1,284 場域 / 4,832 台。明細表的 pager 是假的（寫死 1/2/3/…/143）。字卡全部是硬編碼常數，任何篩選都不可能連動。

**預計改動**

1. `FieldRecord` 新增欄位：

   | 欄位 | 型別 | 說明 |
   |---|---|---|
   | `model` | `string` | 機型（`CS101` / `CS201` / `CS301` / `CS500` / `未登錄`） |
   | `power` | `'開機' \| '關機' \| '離線'` | 場域主要電源狀態 |
   | `mode` | `UsageMode` | 占比最高的使用模式 |
   | `humidity` | `number` | 平均相對濕度 % |
   | `temp` | `number` | 平均溫度 °C |
   | `devOnline` / `devTotal` | `number` | 連網 / 總設備數（`dev` 字串由此推導） |
   | `urgentParts` | `number` | 耗材「立即處理」的設備數 |
   | `alarmDevices` | `number` | 有未解除警報的設備數 |

2. 3 筆真實設備列的新欄位**一律由 `DEVICE_REPORTS` 推導，不得手填**：
   - `model` ← `meta.model`，空字串顯示 `未登錄`（**不得補假機型**）
   - `humidity` ← `meta.humidityAvg`
   - `temp` ← `daily[].temp` 平均
   - `mode` ← `modes[0].label`（時數占比最高者）
   - `power` ← `runStates` 中「正常運轉」時數 vs「關機」時數
   - `urgentParts` ← `consumables` 有 `urgency === '立即處理'` 則 1
   - `alarmDevices` ← `meta.lastAlarmCode !== 0` 則 1（三台目前皆為 0）

3. 9 筆手寫示範列手動補齊新欄位，**既有數字（`q` / `pm` / `cat` / `hrs` / `minPct`）一律不動**。

4. 新增 `FIELDS_A_POP`：`[...FIELDS_A_FULL, ...生成的 1,272 筆]` = 1,284 筆。
   - 以固定 seed 的 mulberry32 PRNG 生成，重整頁面數字不變
   - 分布刻意對齊現有檯面數字：
     - 六大類型比例 = `CATEGORY_DIST`（412 / 386 / 248 / 124 / 78 / 36）
     - `Σ devOnline` = 4,832（對齊 `TODAY_POWER_ON.total`）
     - 開機率 ≈ 87.5%（對齊 `TODAY_POWER_ON.pct`）
     - 平均 PM2.5 ≈ 2 µg/m³（**與真實設備一致**：三台 90 天 `pm25Avg` 為 1.4 / 3.6 / 2.5）
     - 平均濕度 ≈ 58%
     - 平均 AirCare 分數 ≈ 82
   - 生成列一律視為示範資料，`customerName` 使用非真人的示範名稱（AGENTS.md §7）

5. `getFieldDetail()` 的 fallback 查表由 `FIELDS_A_FULL` 改為 `FIELDS_A_POP`，讓生成列點進場域詳情時仍能帶出自己的欄位，而非落到第一台真實設備的骨架。

**API / DB / 外部服務影響**：無（純 mock）。

**驗收條件**
1. `FIELDS_A_POP.length === 1284`
2. `Σ devOnline === 4832`
3. 依 `cat` 分組的筆數等於 `CATEGORY_DIST`
4. 未篩選時：平均 PM2.5 四捨五入 = 2、平均濕度 = 58、平均 AirCare = 82
5. 前 12 筆等於原 `FIELDS_A_FULL` 且欄位值未變
6. 重新整理兩次，任一字卡數字相同（PRNG 決定性）

**風險 / 限制**
- 1,284 筆在模組載入時生成，需確認不影響首屏（生成為純算術，無 I/O）
- 明細表必須真的分頁，否則一次渲染 1,284 列會卡

## 項目 3：七張 KPI 字卡（4 + 3 兩排）

**目標檔案**：`src/modules/module-a/ModuleA.tsx`（`AOverview`）、`src/mocks/module-a-overview.ts`（新增彙總函式）

**目前問題**：現有 5 張字卡（`ModuleA.tsx:122-177`）全為硬編碼；「使用中場域 / 連網裝置 / 空氣品質 / 空氣濕度 / 平均環境健康分數」與需求不符。

**預計改動**

```
第一排  連網設備數 │ 平均 PM2.5 │ 平均濕度 │ 平均溫度
第二排  平均 AirCare 分數 │ 耗材立即處理數 │ 警報設備數
```

| # | 字卡 | 計算式（對 filtered 母體） | 單位 |
|---|---|---|---|
| 1 | 連網設備數 | `Σ devOnline` | 台 |
| 2 | 平均 PM2.5 | `mean(pm)` | µg/m³ |
| 3 | 平均濕度 | `mean(humidity)` | % |
| 4 | 平均溫度 | `mean(temp)` | °C |
| 5 | 平均 AirCare 分數 | `mean(q)` | 分 |
| 6 | 耗材立即處理數 | `Σ urgentParts` | 台 |
| 7 | 警報設備數 | `Σ alarmDevices` | 台 |

- 移除「使用中場域 1,284」字卡；場域總數改在明細表頁尾呈現
- 「平均環境健康分數 82」更名為「平均 AirCare 分數」，沿用 `q`（`airScore`）口徑
- 第一排維持現有大卡樣式（含 sparkline）；第二排三張為 `repeat(3, 1fr)` 同樣式卡
- 字卡副標顯示目前篩選下的母體規模（例：`480 場域 · 1,806 台`），避免使用者誤把篩選後數字當全體

**API / DB / 外部服務影響**：無。

**驗收條件**
1. 未篩選時 7 張數字為：4,832 台 / 2.0 µg/m³ / 58% / 26.6°C / 82 分 / 176 台 / 128 台
2. 版面為 4 + 3 兩排，視窗 1440px 下不換行、不截字
3. 任一篩選變動後 7 張數字同步變動，且與明細表的母體一致

**風險 / 限制**：`.kpi .val` 有 `white-space: nowrap`，第二排長標籤需確認不溢出。

## 項目 4：六個篩選條件（連動字卡 + 明細表）

**目標檔案**：`src/modules/module-a/ModuleA.tsx`、`src/mocks/module-a-overview.ts`（新）

**目前問題**：設備總覽目前只有一個「區域」篩選，且由區域熱圖點擊帶入，沒有獨立篩選列。

**預計改動**

篩選列（`.fb`）置於 tab 下方、字卡上方，六個下拉：

| 篩選 | 選項 |
|---|---|
| 機型 | 全部 / CS101 / CS201 / CS301 / CS500 / 未登錄 |
| 電源 | 全部 / 開機 / 關機 / 離線 |
| 使用模式 | 全部 / 雙智慧 / 清淨智慧 / 除濕智慧 / 手動風量 / 睡眠 / 除臭 |
| PM2.5 區間 | 全部 / 0–15（良好）/ 15–35（普通）/ 35–55（不佳）/ > 55（惡劣） |
| 濕度區間 | 全部 / < 40（過乾）/ 40–50 / 50–60（舒適）/ 60–70 / > 70（過濕） |
| 時間區間 | 近 7 天 / 近 30 天 / 近 90 天（**預設近 90 天** —— AirCare 設備分析報告的統計期就是 90 天，檯面數字也以此為準） |

- 前五個為母體篩選：`FIELDS_A_POP.filter(...)` → 同時餵字卡與明細表
- 「時間區間」不篩母體，而是切換每列的量測值（`pm` / `humidity` / `temp` / `q`）：
  - **3 筆真實設備**：由 `DEVICE_REPORTS.daily` 真算 `slice(-7)` / `slice(-30)` / 全 90 天平均
  - **其餘示範列**：以該列 id 為 seed 的決定性抖動產生三檔數值（近 7 天波動較大、近 90 天最平滑），並在篩選列標註「示範列的區間差異為決定性示意值」
- 保留既有「區域」篩選（由區域熱圖點擊帶入），與六個新篩選以 AND 結合
- 篩選列右側顯示「已套用 N 項 · 清除」
- 同畫面其餘吃同一母體的卡片一併連動，否則會出現「21 場域」與「全 1,284 場域」兩套數字：
  **六大類型分布**（含派工解讀戶數）、**建議聯繫客戶**（三張 upsell 卡的戶數）、
  **健康度 Top 5**、**需關注 · 健康度 < 75**。
  唯一維持靜態的是**類型流動 · 本月遷移** —— 它是每週快照的差分，沒有逐場域的歷史類型可篩，
  已在該卡副標註明「全體母體（不受篩選影響）」

**明細表**
- 資料源由 `FIELDS_A_FULL`（12 筆）改為 filtered 母體
- 新增欄位：機型、電源、使用模式、濕度、溫度（既有欄位保留）
- pager 改為真的分頁（每頁 20 列），頁尾顯示 `第 x–y 筆 · 共 N 筆`

**API / DB / 外部服務影響**：無。

**驗收條件**
1. 六個下拉皆可獨立作用，且可疊加
2. 任一篩選變動後，字卡 7 張數字與明細表筆數同源一致
3. 切換時間區間，字卡的 PM2.5 / 濕度 / 溫度 / AirCare 分數改變，母體筆數不變
4. 3 筆真實設備列在近 7/30/90 天的 PM2.5 與 `DEVICE_REPORTS.daily` 手算結果相符
5. 「清除」可一鍵回到未篩選狀態
6. 分頁翻頁不重算母體（`useMemo`）

**風險 / 限制**
- 六個下拉 + 區域 chip 在 1280px 以下會換行，需確認 `.fb` 的 `flex-wrap` 表現
- 篩選後母體可能為 0 筆，字卡需顯示 `—` 而非 `NaN`

## 驗證方式

```bash
npm run build     # tsc + vite build
npm run lint
git diff --check
```

加上人工 smoke：
1. `/module-a` → 確認 tab 名為「設備總覽」
2. 未篩選狀態核對 7 張字卡數字與驗收條件
3. 逐一切換六個篩選，確認字卡與表同步
4. 切到「分類概況」「場域清單」「個人場域資訊」確認未被本次改動影響
5. 點明細表任一生成列 → 場域詳情能帶出該列欄位（不是第一台真實設備）
