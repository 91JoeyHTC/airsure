## 做了什麼

### 1. 分群：六類型 → 七分群，且改由 P×H 矩陣推導

`CatId` 擴為 `'1'..'7'`，`CATEGORIES` 改用 v2 官方分群名稱：

| id | v2 分群（`code`） | 對外文案（`customer`，v2 §5） | 處置 |
|---|---|---|---|
| 1 | 金級空氣 | 金級空氣 | ok |
| 2 | 銀級空氣 | 銀級空氣 | ok |
| 3 | 銅級空氣 | 銅級空氣 | attention |
| 4 | 濕度風險 | 濕度管理待改善 | attention |
| 5 | 清淨風險 | 空氣清淨待改善 | attention |
| 6 | 清淨除濕雙風險 | 空氣與濕度皆待改善 | warning |
| 7 | **乾燥**（新增） | 空氣偏乾 | ok |

新增 `segmentOf(pm, humidity)` 實作 v2 §3.1–3.4：濕度 ≤45% 優先覆蓋為乾燥，
其餘走 P1–P4 × H1–H4 矩陣。**全站唯一的分群判定**，其他地方一律呼叫它。

### 2. 評分：實作 v2 §4 公式

`pm25Score()` / `humidityScore()` / `aircareIndex()` 逐段照抄 v2 的分段線性函數。
`FieldRecord.q`、`FieldDetail.dhi`、詳情頁 `airScore.*` 全部由公式產出，不再手填或抽樣。

分群與評分刻意分離（v2 §2）：兩者吃同樣的兩個平均值，但規則不同，不得由分數反推分群。

### 3. 級距：兩張分布卡改 v2 門檻，且改為即時計算

| 卡 | 舊 | 新 |
|---|---|---|
| 空氣品質 | 優 <15 / 良好 15–25 / 普通 25–50 / 不佳 ≥50（4 級，室外 AQI 量級） | 極淨 0–5 / 優良 >5–12 / 尚可 >12–15 / 待改善 >15–30 / 不健康 ≥30（v2 §4.1 報告級距） |
| 濕度控制 | 過乾 <40 / 舒適 40–60 / 偏濕 60–75 / 過濕 ≥75（4 級） | HH 過乾 ≤45 / H1 舒適 >45–60 / H2 略偏濕 >60–65 / H3 偏濕 >65–75 / H4 過濕 >75（v2 §3.3 分群等級） |

`n` / `pct` / `catIds` 不再寫死：筆數由當前 filtered 母體算，每一級下方的分群 chip 也是算出來的。
順手修掉 plan 點名的破口 —— 舊版「過乾」那一級的 `catIds` 是空陣列，18 個場域對不到任何類型。

**篩選下拉與分布卡共用同一份級距定義**（`PM_BUCKETS` / `HUMIDITY_BUCKETS` 由
`AIR_QUALITY_DIST` / `HUMIDITY_DIST` 展開），否則下拉寫「過乾 <40%」而卡片畫「≤45%」。

### 4. 卡片排列順序

設備總覽由上而下：篩選列 → KPI 七格 → 母體來源 → **空氣品質 ｜ 濕度控制** →
**七分群分布 ｜ 類型流動** → 建議聯繫客戶 → Top5 ｜ 需關注 → 區域熱圖 → 明細表。

兩張級距卡從「分類概況」搬過來（不是複製），理由是級距是分群的兩個輸入軸，
擺在七分群分布上面才能由「級距 → 分群」順著讀。分類概況剩 4 張卡，版面照舊。

### 5. mock 母體重建（1,284 場域）

生成順序**倒過來**：先依 `CATEGORY_DIST` 排出分群序列，再從該分群允許的 P×H 格內抽
pm 與濕度。這樣分布筆數精確等於目標，而且每一列都能通過
`segmentOf(pm, humidity) === cat` 的反向驗證。先抽數值再看落在哪群，沒辦法命中指定比例。

## 真實三台的分數：改用 v2 重算

三份設備報告存的 `airScore` 是 45.3 / 46.4 / 47.6，因為 `humidityScore` 全為 **0.0**；
但同一份報告的 `humidityAvg` 是 46.8–59.5，依 v2 §4.2 應該得 **100 分**。
這是舊 `scoring_config` 的已知矛盾，repo 內原本就有註記。

沿用報告分數會讓明細表出現「分群＝金級空氣、狀態＝異常」的自相矛盾列。
v2 §7 明定生效公式以 DB `active` 設定為準，而本次核對的 active 版本就是 v2，
因此**檯面一律用 v2 重算**（96 / 98 / 99）；報告原值保留在 `DEVICE_REPORTS.meta`，
不覆寫，需要對照舊版計分時仍查得到。

同時修正一個語意錯誤：`DEVICE_ROWS.pm` 原本取 `daily` 最後一天的平均，
但 v2 分群與評分的輸入是**分析期間平均**，已改為 `meta.pm25Avg`。

## 已知限制

- **`CATEGORY_FLOWS`（類型流動）不吃篩選也未加乾燥群**：它是每週分群快照的差分，
  `dir: 'up'|'down'` 的二元模型對乾燥不適用（乾燥不是「差」，往金級也不是單純「改善」）。
  已在卡片副標註明「全體母體（不受篩選影響）」。待 v2 §10 營運優先序確認後另案。
- **`FIELD_DETAIL_WANG` 的 90 天序列平均與 `airScore.pm25Avg` 對不上**（序列 ~14 vs 34.2）。
  此不一致在本輪之前就存在（舊值 ~14 vs 22.4），未擴大處理。
- **plan 項目 2（`dataStatus` 資料狀態四分類）與項目 3（揭露資格改判分數）未做** ——
  使用者本輪只裁決了項目 1 的範圍。v2 §2.2 指出實測 23% 設備資料不足，
  真實資料接入前需要補這塊。
- 生成列的場域名只有 140 種組合，翻頁會看到重複場域名（示範資料避開門牌號的取捨）。

## 型別改動

- `PowerState` 由 `開機／關機／離線` 改為 **`開機／關機／水箱滿`**。
  停機原因分開記才知道要派工還是推倒水提醒；水滿停機是報告 `runStates` 裡實際有的狀態
  （三台真實設備都有，時數 22.3–801.1h）。真實列的 `power` 改由
  「水滿停機時數 vs 關機時數」推導。
- `FieldRecord` 新增 `devTankFull`：未運轉台數中因水滿停機的部分。
  生成列取未運轉台數的 4 成，`power === '水箱滿'` 的列則全數計入。

## 圖表設計（依 dataviz skill 的程序）

1. **形式**：part-to-whole → 甜甜圈（使用者指定），圖例即資料表，識別不靠顏色單一管道。
2. **色盤**：以 AirSure 品牌三色為基底延伸七色，**跑過驗證器**：
   ```
   node scripts/validate_palette.js \
     "#0D9488,#D97706,#4F46E5,#DC2626,#0284C7,#EA580C,#7C3AED" \
     --mode light --surface "#FFFFFF"
   → 亮度帶 / 色度下限 / CVD 分離 / 一般視覺floor / 對比 全數 PASS
   ```
   順序固定不循環；「關機／關閉／其他」用退位灰 `#9CA3AF`，不佔類別色位。
   *註：品牌主色 `#0E7A66` 色度 0.094 未過下限（讀起來偏灰），故資料視覺化改用
   同色系但更飽和的 `#0D9488`；UI 主色不動。*
3. **切片上限**：甜甜圈超過 6–7 段就分不出來。風速原始 10 級折成 7 段，
   尾端四級（4 強風 / 3 大風 / 6 除濕大 / 8 除臭風量）併為「其他風速」，
   折進去的項目在圖例第二行逐項列出，**數字沒有消失**。
4. **標記**：段與段之間留 2px 底色縫；hover 該段加寬 5px、其餘降到 35% 透明度。
5. **互動**：滑鼠移到環上或圖例列，中心讀數換成該段的數值與佔比；每段附 `<title>`。
6. **文字**：數值與標籤一律用 ink token，顏色只由色塊承載。

## 已知限制

- **風速卡不吃篩選**，因為母體沒有 `fanSpeed`。要讓它連動，需在 `FieldRecord`
  加一個 0–9 的風速欄位並重新取樣母體。
- 電源狀態的「開機 87.6%」是**今日有運轉**的口徑（對齊 `TODAY_POWER_ON`），
  不是即時快照。使用者截圖的 57/30/13 是即時快照，母體沒有這個維度。
